## 3. ما أثبته Production

### 3.1 فصل الأدوار
ثبت وجود المفاتيح الخارجية التالية:
- `runsheets.deliverer_id → users.id`
- `runsheets.driver_id → users.id`
- `runsheets.vehicle_id → vehicles.id`

إذًا لا يجوز لواجهة مشرف التوصيل تعديل `driver_id` لتعيين المندوب، ولا يجوز لها تغيير السائق أو المركبة أثناء إسناد المندوب.

### 3.2 عقد الإسناد المركزي
Production يحتوي الدالة:
`delivery_supervisor_assign_deliverer_atomic(uuid, text, uuid, text)`

وتتحقق من هوية المستخدم والشركة والصلاحية، وتتحقق من أن المندوب المستهدف نشط ومنتمي إلى الشركة ومؤهل بصلاحية `delivery`، وتقيّد الإسناد/فك الإسناد بحالة `Loaded`، وتستخدم `operation_id` عبر `erp_operation_registry` لمنع التكرار المتعارض.

ACL المقروءة من Production:
- `authenticated`: EXECUTE.
- `service_role`: EXECUTE.
- لا يوجد EXECUTE لـ`anon` أو `PUBLIC` ضمن ACL الفعلية المقروءة.

### 3.3 الشكاوى
جدول `service_complaints` موجود في Production، ويتضمن `company_id`, `source_type`, `employee_id`, `runsheet_id`, `order_id`, `complaint_type_id`, `status`, `description`, `resolution` وغيرها، مع علاقات إلى المستخدمين والرانشيتات والطلبات وأنواع الشكاوى.
الجدول لا يحتوي حاليًا حقولًا مستقلة صريحة لهوية مُقدّم الشكوى/اسم القسم/وسيلة التواصل. لذلك يمكن عرض مصدر الشكوى المسجل وبيانات الموظف المعني، لكن لا يمكن إثبات اسم المُبلّغ إذا لم يُخزّن أصلًا.
الاستعلام التجميعي المباشر لم يُظهر شكاوى مسجلة في الوقت الذي فُحصت فيه قاعدة البيانات؛ هذا لا يثبت عدم وجود شكاوى تاريخية خارج النطاق أو في مصادر أخرى.

### 3.4 حدود الدليل
لم يتم تشغيل اختبار إيجابي عبر جلسة مستخدم مصادق عليها، ولم يتم تنفيذ تغيير إسناد على رانشيت أعمال حقيقية. لذلك لا أعتبر هذه المهمة مكتملة E2E أو Production Runtime Verified.

## 4. الإصلاحات المنفذة

### 4.1 تطبيق مشرف التوصيل
تم تحديث `companies/company-1/delivery/supervisor.html` كي:
1. يستخدم `delivery_supervisor_assignment_query` لعرض لوحة الأداء والفريق والرانشيتات بدل القراءة المباشرة غير المقيّدة صراحةً بسياق الشركة.
2. يستخدم `delivery_supervisor_assign_deliverer_atomic` للإسناد وفك الإسناد؛ لم يعد يكتب `driver_id` مباشرة.
3. يخصص ويعرض `deliverer_id` كمندوب، ويعرض `driver_id` و`vehicle_id` كبيانات مستقلة للقراءة فقط.
4. لا يسمح بعملية «سحب اضطراري» غير معتمدة بعد انتقال الرانشيت إلى `Delivering`; يعرض تنبيهًا بدل تغيير الحالة أو العبث بالتكليف.
5. يضيف تبويب «الشكاوى» لعرض الشكاوى حسب الشركة، عبر RPC محمي، مع بيانات النوع والمصدر والموظف المعني والرانشيت والطلب والوصف والحل إن وجد.
6. يضيف ترميز HTML للنصوص الديناميكية المعروضة لتقليل خطر إدخال HTML/JavaScript غير موثوق.
7. يغيّر تسمية واجهة الفريق من «السائقين» إلى «المندوبون».

**اختبار ساكن منفذ:** جرى تحليل كتل JavaScript المضمّنة في الملف بعد التعديل باستخدام parser في بيئة التنفيذ؛ عدد أخطاء الصياغة = 0. كما تم التحقق نصيًا من وجود استدعاء RPC المركزي، ومن عدم بقاء نمط الكتابة المباشرة `update({driver_id:...})`.

### 4.2 عقد قراءة الشكاوى
أُنشئت في Supabase Production الدالة:
`delivery_supervisor_complaints_query(uuid)`

خصائصها:
- `SECURITY DEFINER` مع `search_path` محدد.
- تشترط جلسة مصادقة `auth.uid()`.
- تتحقق من ارتباط المستخدم النشط بالشركة المطلوبة.
- تتحقق من صلاحية `*` أو `delivery_supervisor` أو `fleet.read` أو `fleet.manage`.
- تقصر القراءة على `service_complaints.company_id = p_company_id`.
- تربط نوع الشكوى والموظف والرانشيت والطلب باستخدام joins مقيدة بسياق الشركة.
- لا تنشئ جدول شكاوى مكررًا.
- ACL Production: `authenticated` و`service_role` فقط، دون `anon` أو `PUBLIC`.

**اختبار أمني سلبي منفذ:** استدعاء الدالة دون جلسة مصادق عليها رُفض بالرسالة `جلسة مصادقة مطلوبة`. هذا يثبت بوابة المصادقة السلبية فقط، وليس نجاح الاستدعاء للمستخدم المصرح له.

## 7. نقاط متبقية صريحة — لا تُخفى

1. **E2E مصادق عليه:** يجب تنفيذ تسجيل دخول فعلي ثم اختبار عرض الفريق والرانشيتات والشكاوى والإسناد وفك الإسناد على بيانات اختبار معزولة.
2. **HTTP/deployment parity:** يجب جلب `supervisor.html` من عنوان الإنتاج ومقارنة السلوك/المحتوى مع Git بعد معرفة عنوان النشر الفعلي. لا أملك هنا دليلًا كافيًا لإعلان النشر مكتملًا.
3. **هوية مُقدّم الشكوى:** `service_complaints` لا يسجل حاليًا `reporter_user_id` أو `reporter_department` أو `reporter_name` صراحةً. لا يجوز اختراع هذه القيم من `employee_id` لأنه يمثل الموظف المعني بالشكوى، وليس بالضرورة مقدمها.
4. **تدفق الشكاوى في تطبيق المندوب:** المصدر الحالي الذي تمت مراجعته يكتب `company_id` بقيمة UUID ثابتة، ويولّد `complaint_code` من أحدث سجل قبل الإدراج؛ وهذا قد يسبب خللًا في عزل الشركات/تزامن إنشاء الأكواد. لم أعدّل هذا التدفق في هذه الوحدة لأن ذلك يحتاج عقدًا موحدًا للمُبلّغ ورقم الشكوى واختبارًا رجعيًا لجميع المستهلكين.
5. **ملف البرومبت المرجعي:** الرابط `MASTER_CTO_EXECUTION_PROMPT_LOADER_PICKER_INTEGRATION_20261025.md` أعاد 404 عبر أداة GitHub، ولم أستطع إثبات محتواه التاريخي. استُخدمت متطلبات المهمة الملصقة في رسالة المالك كأساس مباشر بدل اختلاق محتوى للملف المفقود.
